# MONSTER 制片系统新架构

## 1. 项目定位

这是一个围绕 AI 动画项目管理的制片系统。

页面不是通用看板，而是围绕 `MONSTER` 项目的实际生产流程来搭建，核心推进板块只有 4 个：

1. 剧本开发
2. 资产管理
3. 分镜制作
4. 后期

其中，分镜制作是当前最关键的展开面板，需要支持：

- 19 场戏
- 298 个镜头
- 截止时间：2026-04-15 完成全部图片分镜
- 每镜任务列表
- 每镜状态
- 每镜负责人
- 每日推进记录

## 2. 落地方式

建议把这个产品理解为：

- 一个 React 前端
- 运行在飞书 Base 插件环境里
- 在浏览器中直接读取飞书多维表格数据
- 在浏览器中完成计算、聚合、渲染和录入
- 只有 Gemini 调用走一个很薄的后端代理

这意味着我们不再以“服务端同步表格 -> 本地 JSON”作为主路线，而是以“前端实时读表 + 前端实时计算”为主路线。

## 3. 为什么这样做

### 3.1 飞书侧

Base JS SDK 文档说明它是 Base 插件开发文档，`bitable` 是 API 入口，并且可以直接在前端获取当前表、字段、记录等对象。

参考：

- [Base JS SDK 首页](https://lark-base-team.github.io/js-sdk-docs/zh/)
- [Base JS SDK 核心知识](https://lark-base-team.github.io/js-sdk-docs/zh/start/core)

文档里明确展示了：

- `import { bitable } from '@lark-base-open/js-sdk'`
- `const table = await bitable.base.getActiveTable()`

这说明最合适的形态是“飞书 Base 插件前端”，而不是普通外链网页去模拟飞书。

### 3.2 Gemini 侧

Gemini 官方文档当前仍然给出了 `gemini-3-flash-preview` 的 JavaScript 和 REST 示例，但同时明确提醒不要在生产环境把 API key 暴露在浏览器端。

参考：

- [Gemini API keys](https://ai.google.dev/gemini-api/docs/api-key)
- [Gemini models](https://ai.google.dev/gemini-api/docs/models)

因此：

- 飞书数据：前端直读
- Gemini：走服务端代理

这是最贴近你需求、同时又比较安全的做法。

## 4. 产品结构

## 4.1 页面结构

页面只做 4 个主模块：

1. 剧本开发
2. 资产管理
3. 分镜制作
4. 后期

顶部是项目头部信息：

- 项目名
- 今日日期
- 总体完成率
- 距离 2026-04-15 还剩多少天
- 今日完成条数
- 风险提醒

中间是 4 个模块卡片。

点击任意模块，右侧或下方展开详情面板。

## 4.2 模块展开逻辑

### 剧本开发

子项：

- 剧本主线梳理
- 分集大纲
- 分集剧本

交互：

- 每个子项有一个圆圈状态按钮
- 可单独切换状态
- 模块整体支持一键切换状态
- 可以显示负责人、更新时间、备注

### 资产管理

子项：

- 人物设计
- 场景设计

交互：

- 支持单项状态切换
- 支持整体状态切换
- 支持展示当前负责人、数量、备注

### 分镜制作

这是系统核心。

先显示模块摘要：

- 当前总镜头数：298
- 当前已完成镜头数
- 当前进行中镜头数
- 当前未开始镜头数
- 当前负责人分布
- 剩余天数
- 按当前速度是否能在 2026-04-15 前完成

展开后按“场次 -> 镜头”双层结构展示：

- 场次列表：19 场
- 每场下面是镜头列表
- 每镜显示：
  - 镜号
  - 场次
  - 内容描述
  - 当前状态
  - 当前负责人
  - 是否已完成
  - 更新时间

并提供统计：

- 每场完成率
- 每人负责镜头数
- 每人已完成数
- 预计完成时间

### 后期

子项：

- 视频制作
- 音乐后期

交互：

- 单项状态切换
- 模块整体状态切换
- 展示负责人、进度、备注

## 5. 数据模型

## 5.1 推荐飞书表结构

为了贴近你当前项目，不建议继续沿用“10 道工序通用表”的思路，而建议改成业务表结构。

### 表1：项目总控表

一行一条项目记录。

建议字段：

- 项目名
- 总镜头数
- 总场次数
- 图片分镜截止日期
- 今日目标
- 当前阶段
- 总完成率
- 风险备注

### 表2：剧本开发表

一行一条剧本任务或阶段记录。

建议字段：

- 模块
- 子项
- 状态
- 负责人
- 开始时间
- 更新时间
- 备注

### 表3：资产管理表

一行一条资产任务。

建议字段：

- 资产类型
- 名称
- 状态
- 负责人
- 关联场次
- 备注

### 表4：分镜制作表

这是最核心的表，一镜一行。

建议字段：

- 镜号
- 场次
- 内容描述
- 当前状态
- 当前负责人
- 计划开始日期
- 完成日期
- 参考画面
- 确定画面
- 方向
- 备注

### 表5：AI 图片分镜任务表

一行一条图片生成任务。

建议字段：

- 关联镜号
- 场次
- 提示词
- 参数
- 版本号
- 状态
- 负责人
- 输出图
- 备注

### 表6：后期制作表

一行一条后期任务。

建议字段：

- 后期类型
- 关联场次
- 关联镜号
- 状态
- 负责人
- 备注

### 表7：协作记录表

这个表同时承载：

- 每日工作日志
- 审核记录

建议字段：

- 记录类型：`daily_log | review`
- 日期
- 人员
- 模块
- 子项
- 关联场次
- 关联镜号
- 内容
- 状态变更前
- 状态变更后

这样就不需要再额外多一张“日志表”，也能保留你原来图里的审核思路。

## 5.2 前端内存态

前端不要直接把表结构暴露给组件，而是在浏览器里聚合成 4 个 domain 对象：

```ts
type ProjectState = {
  project: ProjectSummary;
  script: ScriptModuleState;
  assets: AssetModuleState;
  storyboard: StoryboardModuleState;
  post: PostModuleState;
  logs: CollaborationLog[];
};
```

也就是说：

- 飞书表是数据源
- React 组件只吃前端聚合后的内存态

## 6. 浏览器内计算逻辑

## 6.1 总体进度

总体进度不再按统一“工序节点数”来算，而按业务模块加权：

- 剧本开发 20%
- 资产管理 20%
- 分镜制作 45%
- 后期 15%

这里分镜制作权重最高，因为它是当前核心。

## 6.2 分镜模块计算

输入：

- 总镜头数：298
- 已完成镜头数
- 当前日期
- 截止日期：2026-04-15
- 最近每日完成数

输出：

- 今日完成数
- 剩余镜头数
- 剩余天数
- 目标日均产出
- 当前日均产出
- 是否存在延期风险

公式：

- 剩余镜头数 = 298 - 已完成镜头数
- 剩余天数 = 截止日期 - 今天
- 目标日均产出 = 剩余镜头数 / 剩余天数
- 当前日均产出 = 最近 N 天完成镜头数 / N

你提到“从今天开始每天完成 5 条”，这可以作为默认基线速度。

## 6.3 每场进度

每场统计：

- 该场总镜头数
- 该场已完成镜头数
- 该场进行中镜头数
- 该场未开始镜头数
- 该场完成率

## 6.4 人员分工

按负责人统计：

- 总负责镜头数
- 已完成镜头数
- 进行中镜头数
- 今日完成数

## 7. 录入区设计

录入区必须放在前端页面里，且足够快。

录入内容：

- 选日期
- 选人
- 一句话描述今天做了什么
- 回车保存

保存逻辑：

1. 写入表7 协作记录表
2. 如果内容里带有状态更新，顺手更新对应业务表
3. 页面本地重新计算统计结果

团队成员可以直接新增。

因此人员下拉框应该允许：

- 选已有成员
- 输入新成员并创建

## 8. 状态切换逻辑

每个模块和每个子项都支持状态切换。

状态建议统一为：

- 未开始
- 进行中
- 已完成
- 阻塞

交互：

- 点击圆圈切换单个子项状态
- 点击模块头部按钮批量切换整个模块状态

如果模块整体切换为“已完成”，则默认把其所有未完成子项一并更新为“已完成”。

## 9. Gemini 接口设计

Gemini 不负责主数据读取，只负责“辅助生成”。

推荐只做 4 个接口：

### POST `/api/gemini/script-refine`

用途：

- 优化剧本主线
- 拆分分集大纲
- 润色分集剧本

请求体：

```json
{
  "module": "script",
  "task": "episode_outline",
  "context": {},
  "prompt": "根据主线梳理输出第3集大纲"
}
```

### POST `/api/gemini/storyboard-assist`

用途：

- 根据场次和剧情生成文字分镜建议
- 根据漫画内容转成图片分镜描述
- 补镜头说明

请求体：

```json
{
  "module": "storyboard",
  "scene": "第九场",
  "shotNo": 112,
  "description": "男人看向瘦狗",
  "prompt": "补充这个镜头的文字分镜和AI图片描述"
}
```

### POST `/api/gemini/image-prompt`

用途：

- 生成 AI 图片提示词
- 统一角色和场景风格

### POST `/api/gemini/daily-summary`

用途：

- 根据当天日志自动生成制片日报

## 9.1 Gemini 模型

当前可以按你指定的 `gemini-3-flash-preview` 设计。

官方文档里仍提供了这个模型的 JS 与 REST 示例：

- [Gemini API keys](https://ai.google.dev/gemini-api/docs/api-key)

但生产环境不能把 key 直接暴露到浏览器。

因此实际调用结构应为：

```text
React 前端 -> 你自己的轻量代理接口 -> Gemini API
```

而不是：

```text
React 前端 -> 直接带 API key 调 Gemini
```

## 12. 当前结论

这次我们重新回到正确思路：

- 不是做抽象化通用 dashboard
- 而是做一个围绕 `MONSTER` 项目的真实制片系统
- 前端是 React
- 数据主来源是飞书多维表格
- 计算和渲染在浏览器里完成
- Gemini 只做辅助生成，不做主数据源

后续代码重构都应该围绕这个文档执行。
